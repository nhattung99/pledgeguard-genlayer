## Observations and lessons

### Publication and verification are separate steps

A completed document must be accessible to the reviewer, but accessibility alone does not establish when it was created or published. Keeping the deliverable and timestamp reference as two separate inputs makes this distinction visible and easier to check.

### Specific links are more useful than broad links

A permanent file link and the matching commit record form a clear pair. Repository homepages, profile pages, and unrelated commit histories require additional inference and can obscure which work is actually being submitted.

### Transaction status requires careful interpretation

PledgeGuard has distinct creation, evidence-submission, and review transactions. A failed creation should not be treated as an existing pledge. A successful evidence submission should be followed by a visible `SUBMITTED` state before requesting review. A verdict is separate again from confirmation that a payout recipient has actually been credited.

### Readable evidence is still subject to adjudication

Public links can encounter renderer restrictions or access failures. A clear document and a matching commit improve the evidence trail, but they do not guarantee access by every renderer, validator agreement, a positive verdict, or a refund.

## Submission workflow prepared

1. Obtain the permanent public URL for this report at its publication commit.
2. Obtain the public URL for the same commit as the timestamp reference.
3. Open pledge `0` in PledgeGuard and enter those URLs in the deliverable and reference fields.
4. Submit evidence once, then wait for the attempt count and status to update.
5. Request AI review only after the evidence submission succeeds.
6. Read the verdict, confidence, and reason. If more evidence is required, make genuine improvements and use a remaining attempt within the deadline.
